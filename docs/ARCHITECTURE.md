# Архитектура

## Выбор стека: WebView + React

Приложение построено как нативная Android-оболочка с полноэкранным `WebView`,
внутри которого работает React-приложение из `assets`.

**Почему так:**

- интерфейс для 7–11 лет требует много визуальных состояний, анимаций и
  нестандартных элементов — на CSS/SVG это делается быстрее, чем на нативных
  вью;
- вся игровая логика остаётся на TypeScript и покрывается тестами без
  Android-окружения — проверка занимает секунды, а не минуты;
- один и тот же код запускается в браузере (`npm run dev`) и в APK: сценарий
  можно отлаживать без устройства;
- путь к публикации в RuStore сохраняется полностью — это обычный APK.

**Чем платим:**

- нет доступа к нативным анимациям и системным компонентам — для этого
  приложения не требуется;
- `WebView` разный на разных устройствах; поэтому используются только широко
  поддержанные возможности (ES2019, CSS Grid/Flexbox, `localStorage`) и не
  используется ничего, что появилось позже Android 8.

Важная техническая деталь: содержимое отдаётся не через `file:///android_asset`,
а через `WebViewAssetLoader` по адресу `https://appassets.androidplatform.net/`.
По схеме `file://` WebView считает страницу «непрозрачным источником» и
блокирует `localStorage`, на котором держится всё сохранение прогресса.

└───────────────────────────┬─────────────────────────────────┘
┌───────────────────────────▼─────────────────────────────────┐

Зависимости идут строго сверху вниз. `domain/` не знает про React, `content/`
не знает про экраны, экраны не считают экономику сами.

## Компоненты

### `domain/` — игровая экономика

| Модуль | Ответственность |
| --- | --- |
| [`rules.ts`](../web/src/domain/rules.ts) | Все числовые константы: доходы, пороги, очки роста. Меняются без правки логики. |
| [`types.ts`](../web/src/domain/types.ts) | Типы предметной области. |
| [`budget.ts`](../web/src/domain/budget.ts) | Проверка плана, остаток, сравнение плана с фактом. |
| [`purchase.ts`](../web/src/domain/purchase.ts) | Допустимость покупки, объяснение отказа, варианты выхода. |
| [`savings.ts`](../web/src/domain/savings.ts) | Прогресс цели, средняя сумма пополнения, срок, предпросмотр снятия. |
| [`period.ts`](../web/src/domain/period.ts) | Закрытие периода: очки роста, объяснения, следующий шаг. |
| [`pet.ts`](../web/src/domain/pet.ts) | Показатели состояния, настроение, стадии развития. |
| [`quests.ts`](../web/src/domain/quests.ts) | Проверка ответов на задания всех пяти видов. |
| [`state.ts`](../web/src/domain/state.ts) | Создание профиля, тестовый профиль, миграция схемы. |

Все функции чистые: на вход — данные, на выход — данные. Побочных эффектов нет,
поэтому 86 доменных тестов выполняются за доли секунды.

### `store/gameStore.tsx`

Единственное место, где состояние меняется. Реализовано на `useReducer`:
каждое действие (`buy`, `deposit`, `withdraw`, `endPeriod`, …) — отдельная ветка
без побочных эффектов, кроме записи в журнал `ledger`.

Автосохранение висит на `useEffect` по изменению состояния: отдельной кнопки
«сохранить» ребёнку не нужно, а прогресс не теряется при внезапном закрытии.

### `content/` — учебный контент

Отделён от интерфейсного кода (ТЗ п. 3.2). Это обычные типизированные массивы:

| Файл | Содержимое |
| --- | --- |
| [`quests.ts`](../web/src/content/quests.ts) | 9 заданий по 3 темам |
| [`shop.ts`](../web/src/content/shop.ts) | 12 позиций каталога |
| [`goals.ts`](../web/src/content/goals.ts) | 4 цели + части конструктора своей цели |
| [`appearance.ts`](../web/src/content/appearance.ts) | Виды, палитры, аксессуары, стадии роста |
| [`glossary.ts`](../web/src/content/glossary.ts) | 10 терминов и 4 слайда знакомства |

Каждая запись контента ссылается на иконку по имени из `IconName` — контент
задаёт, *что* показать, а слой отображения решает, *как* это нарисовать.

### `screens/` и `components/`

Экраны не считают экономику. Например, `ShopScreen` не решает, хватает ли денег,
— он вызывает `checkPurchase()` и отображает результат. Благодаря этому правило
«отрицательный баланс невозможен» проверяется тестом, а не внимательностью при
вёрстке.

Общие элементы собраны в [`ui.tsx`](../web/src/components/ui.tsx): каркас
`AppShell` с шапкой и панелью вкладок, кнопки, карточки, счётчик суммы, полосы
и кольцо прогресса, модальные окна и подтверждения. Экраны возвращают только
содержимое — шапку и вкладки рисует каркас, поэтому кнопка возврата и баланс
находятся на одном месте везде.

[`Icon.tsx`](../web/src/components/Icon.tsx) — набор из 53 линейных иконок,
описанных путями SVG. Имя иконки (`IconName`) объявлено в доменных типах, а
рисование живёт в слое отображения: `Record<IconName, Shape>` не даст собрать
проект, если для какого-то имени забыли нарисовать иконку.

Оформление задано токенами в [`global.css`](../web/src/styles/global.css);
шрифты Nunito и Onest упакованы локально
([`fonts.css`](../web/src/styles/fonts.css)), потому что приложение работает
офлайн. Подробности — в [REDESIGN.md](REDESIGN.md).

## Схема обновления учебного контента

Добавление задания не требует изменения логики:

1. дописать объект в `QUESTS` в `web/src/content/quests.ts`;
2. выбрать один из пяти видов (`allocate`, `basket`, `order`, `number`,
   `choice`) — у каждого уже есть универсальный проигрыватель;
3. пересобрать веб-слой (`npm run build`) и APK.

TypeScript проверит структуру на этапе компиляции, а `quests.test.ts` и
`content.test.ts` автоматически применят к новому заданию общие проверки:
объяснение выдаётся при любом ответе, награда положительна, идентификаторы
уникальны, минимумы ТЗ соблюдены.

Тот же принцип для товаров (`shop.ts`), целей (`goals.ts`) и внешнего вида
питомца (`appearance.ts`).

Если понадобится новый **вид** взаимодействия — добавляется один проигрыватель
в `QuestPlayScreen.tsx` и одна ветка в `evaluateQuest()`. Существующие задания
при этом не затрагиваются.

## Нативный мост

Оболочки устроены по-разному, и это определило форму моста. Android отдаёт
объект в `window`, его методы вызываются синхронно и возвращают значение. iOS
даёт только односторонние сообщения `postMessage` — вернуть значение нельзя.

Мост разделён так, чтобы обе платформы обслуживались одним кодом:

| Направление | Как устроено |
| --- | --- |
| **Чтение** (версия приложения, сохранённый профиль) | Оболочка **внедряет** значения в `window` до загрузки страницы. Читаются синхронно, без ожидания. |
| **Команды** (`clearAllData`, `saveProfile`, `clearProfile`) | Отправляются без ответа: на iOS через `postMessage`, на Android через `FinniNative.postMessage(json)`. |
| **Возврат** | Оболочка вызывает `window.finniHandleBack()` и смотрит на ответ: системная кнопка на Android, краевой свайп на iOS. |

Поверхность намеренно мала: на Android через `addJavascriptInterface` открыто
два метода, на iOS — один обработчик сообщений. Внешние переходы заблокированы
на обеих платформах: пропускается только собственный источник.

Полная таблица различий между оболочками — в [ios/README.md](../ios/README.md).

## Хранение данных

| Платформа | Где | Формат |
| --- | --- | --- |
| Android и браузер | `localStorage`, ключ `finni.profile.v1` | JSON |
| iOS | Файл `profile.json` в Application Support, пишет оболочка | JSON |

На Android страница отдаётся по https-адресу через `WebViewAssetLoader`, и
веб-хранилище работает штатно. В WKWebView страница живёт на собственной схеме,
а доступность `localStorage` для таких источников от версии к версии менялась —
полагаться на неё нельзя, потому что молча потерянный прогресс хуже любой
видимой ошибки. Поэтому на iOS профиль хранит сама оболочка: читает файл и
внедряет его в страницу до отрисовки, а запись принимает командой.

Выбор хранилища скрыт за одним интерфейсом в `platform/storage.ts` — игровой код
о платформе не знает.

Структура описана в [DATA-MODEL.md](DATA-MODEL.md). Схема версионирована полем
`schemaVersion`; функция `migrate()` дозаполняет отсутствующие поля, чтобы
профиль от старой сборки не ронял приложение.

Room/SQLite сознательно не используются: состояние — один небольшой документ
(единицы килобайт), к которому нет запросов по выборке. Реляционное хранилище
здесь добавило бы мост между Kotlin и JS на каждое действие и стало бы самой
хрупкой частью прототипа. ТЗ п. 3.2 допускает «файловое хранилище или
эквивалент».

Все обращения к хранилищу обёрнуты в `try/catch`: если оно недоступно, игра
продолжает работать, а взрослый видит в своём разделе строку «Хранилище
доступно: нет».

## Сборка

```
                        ┌─► android/app/src/main/assets/www/ ─► gradle ─► APK
web/ ─npm run build─► web/dist ─┤
                        └─► ios/FinniPet/www/ ──────────────► Xcode ─► .app
```

Обе оболочки получают один и тот же артефакт: `web/dist` раскладывает по ним
скрипт `web/scripts/sync-native.mjs` (на Node, потому что Android собирают на
Windows, а iOS — только на macOS).

Копии в оболочках не хранятся в репозитории — это результат сборки. Gradle
проверяет его наличие перед упаковкой (`checkWebAssets`) и, если веб-слой не
собран, останавливается с инструкцией вместо выпуска APK с пустым экраном.
